Learnings :

- Si on veut vérifier si un souci de route vient du back ou du front, on peut faire un curl. Si le curl fonctionne, mais que ça ne marche pas quand on le fait sur le frontend, on a trouvé le responsable.
- [RAPPEL] : console.log dans le backend affiche le code dans le terminal ou Node est executé. Console.log dans le frontend affiche dans la console F12 du navigateur puisque c'est la ou le code frontend s'exécute.
- concurrently : Un outil qui s'installe sur le projet avec npm, et permet de lancer serveur backend et frontend en même temps, et d'avoir les deux affichages de log sur le même terminal avec la liberté de choisir une couleur d'affichage pour chaque.
- [LocalStorage] : Petite zone de stockage permanente dans le navigateur, relié à un domaine. Dans notre cas, on stocke notre JWT dans une partie du LocalStorage liée à notre domaine http://localhost:5173. Cet espace de stockage est permanent, à moi d'un nettoyage volontaire du browser. Il peut être corrompu avec une faille XSS (injection JS).
- [req] : l'objet req qu'on envoie dans un fetch, ne représente pas juste ce que le frontend met dans la request. C'est un objet serveur enrichi par Express. Donc en l'occurence, on retrouve bien nos informations transmises via req.body ou req.header. Mais req en lui même est un objet plus gros.
- [Trajet JWT] : L'user se connecte via le front, on envoie les informations de connections dans le fetch
  - Le backend reçoit les informations, crée un token jwt.sign() qui contient l'userID, l'expiration, et une string crypté avec la clef SECRET_KEY, puis le renvoie au front.
  - Le Front recupère ce token dans data.token, le stocke dans localStorage.
  - à son prochain Fetch, le front transmet ce token dans le req.body.
  - Le middleware backend intercepte le fetch, vérifie la validité du token, le décode, et DEPUIS LE TOKEN RETROUVE L'USER ASSOCIÉ et l'ajoute à req pour la route finale.
  - La route finale check req, voit que dedans il y a userID, et adapte son comportement en fonction.
